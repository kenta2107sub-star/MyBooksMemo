> **プロジェクト名**：MyBooksMemo（読書メモ・言語化トレーニングアプリ）

## サービス概要

毎日本を読む習慣がある個人（開発者自身のみが利用）向けの、読書メモ・言語化トレーニングアプリ。
以下3つの課題を解決する。

1. 本を読んでも内容を忘れる／読み返しが発生する → 毎日記録し、後で簡単に振り返れるようにする
2. 自己啓発本を読んだ際に「自分の日常にどう活かすか」を言語化して記録したい
3. 言語化する習慣をつけ、言語化の質を上げていきたい

## 前提条件

- 利用者：開発者本人のみ（完全個人利用）。将来的な収益化・公開の可能性はゼロではないが、Phase 1ではSaaS化前提の作り込みは行わない
- プラットフォーム：iOSネイティブアプリ（Swift / SwiftUI）
- インターフェース種別：モバイルアプリのネイティブ画面（本ドキュメントでは便宜上 `SCR-XX` の画面IDを仮置きする。正式な画面仕様は `basic_design.md` で確定する）
- ローカルデータ永続化：SwiftData
- AI連携：Google Gemini API（`gemini-3.1-flash-lite`）。iOSアプリはAPIキーを保持せず、Cloudflare Workers（BFF）を経由して呼び出す
- 書誌情報取得：国立国会図書館サーチAPI（SRU、`https://ndlsearch.ndl.go.jp/api/sru`）。個人・非営利利用は申請不要・無料。ISBNは完全一致検索

> このセクションに記載された機能・仕様はPhase 1では**実装しない**。
> Claude Codeはこのリストにある内容をコードに含めないこと。

### 後フェーズに延期
- CloudKitによる複数デバイス間同期：将来的な同期の余地はあるが、Phase 1ではSwiftDataによるローカル永続化のみとする

### 意図的に永久除外
- プッシュ通知・リマインダー：ユーザーが自分のタイミングでアプリを開く前提のため実装しない
- マルチユーザー対応・ログイン／認証機能：完全個人利用のため実装しない
- 課金・サブスクリプション機能：収益化はPhase 1のスコープ外

### 技術的制約による除外
- 書影が国立国会図書館サーチAPIから取得できない書誌に対する代替画像取得（Amazon等の外部APIへのフォールバック）：Phase 1ではNDL APIのみを情報源とし、書影が得られない場合はプレースホルダー画像を表示する

### 前提条件の欠如による除外
- 他ユーザーとのメモ・要約の共有、レビュー投稿：本アプリはローカル完結でサーバー側の共有基盤を持たないため実装しない

## 機能要件

### FR-01：本の登録（バーコードスキャン・ISBN自動取得）

#### 概要（1行）
カメラでISBNバーコードを読み取り、国立国会図書館サーチAPIから書誌情報を自動取得して本を登録する。

#### 対応する画面 / インターフェース
- `SCR-02 本登録画面（スキャン）` → `SCR-04 書誌情報確認画面` → 登録後 `SCR-01 本棚一覧画面` へ遷移

#### 依存関係
- 依存するFR：なし（エントリーポイント）
- 依存されるFR：FR-03（登録済みの本が前提）、FR-07（登録済みの本が削除対象になる）

#### 入力
- バーコード映像（カメラ入力。VisionKitの`DataScannerViewController`が検出するEAN-13シンボロジー）

#### 処理フロー
1. 本棚一覧画面（SCR-01）右上の「＋」ボタンをタップし、本登録画面（SCR-02）を開く
2. SCR-02で `DataScannerViewController`（VisionKit、`.barcode(symbologies: [.ean13])`）を起動し、リアルタイムスキャンを開始する
   - カメラ権限が未許可 → iOS標準の権限リクエストダイアログを表示する
   - カメラ権限が拒否済み → 「カメラへのアクセスが許可されていません。設定アプリから許可してください」とSCR-02上に表示し、あわせて「手入力で登録する」ボタン（FR-02への導線）を表示する
3. バーコードを検出したら13桁のコード文字列を取得する
   - 先頭が `978` または `979` で始まる（ISBN-13） → Step4へ進む
   - それ以外のバーコード（書籍JANコードの追加コード等） → 「書籍のISBNバーコード（978または979で始まる13桁）を読み取ってください」と表示し、スキャンを継続する（Step2に留まる）
4. 読み取ったISBNを国立国会図書館サーチAPI（SRU）に問い合わせる
   - `GET https://ndlsearch.ndl.go.jp/api/sru?operation=searchRetrieve&query=isbn%3D{ISBN}&recordSchema=dcndl&recordPacking=xml`
   - タイムアウト：10秒（FR-06共通ルール参照）
5. レスポンスをXMLパースし、`dc:title`（タイトル）・`dc:creator`（著者）・書影情報を抽出する
   - 検索結果0件 → 「該当する書籍情報が見つかりませんでした」と表示し、「手入力で登録する」ボタン（FR-02への導線）を表示する
   - 検索結果1件 → 書誌情報確認画面（SCR-04）にタイトル・著者・表紙（あれば）を表示する
   - 検索結果2件以上 → 先頭の1件を採用し、SCR-04に表示する（複数候補からの選択UIはPhase 1では作らない）
   - 書影URLがレスポンスに含まれない → 表紙なしとして扱い、SCR-04にはプレースホルダー画像を表示する
6. ユーザーがSCR-04で「この本を登録する」をタップ → SwiftDataに `Book` として保存し、本棚一覧画面（SCR-01）へ遷移する
7. ユーザーがSCR-04で「情報を修正する」をタップ → 取得済みの情報を初期値としてSCR-03（手入力フォーム、FR-02）に遷移し、編集可能な状態で表示する

#### 異常系
- ネットワーク接続なし（バーコード検出時点） → 「インターネットに接続されていません。手入力で登録しますか？」と表示し、「手入力で登録する」ボタン（FR-02への導線）を表示する
- NDL APIタイムアウト（10秒超過）・5xxエラー → 「書籍情報の取得に失敗しました」と表示し、「手入力で登録する」ボタン（FR-02への導線）を表示する
- NDL APIのレスポンスXMLがパース不能（想定外フォーマット） → 検索結果0件と同様に扱い、「該当する書籍情報が見つかりませんでした」と表示する

#### 画面表示例（正常系）
```
SCR-04：
タイトル：嫌われる勇気
著者：岸見一郎, 古賀史健
表紙：あり（サムネイル表示）
[この本を登録する]　[情報を修正する]
```

#### 画面表示例（異常系）
```
「該当する書籍情報が見つかりませんでした」
[手入力で登録する]
```

### FR-02：本の登録（手入力フォールバック）

#### 概要（1行）
ISBN自動取得が使えない場合、または情報を修正したい場合に、書誌情報を手動で入力して本を登録する。

#### 対応する画面 / インターフェース
- `SCR-03 本登録画面（手入力）`

#### 依存関係
- 依存するFR：なし（FR-01から遷移して呼ばれる場合と、独立して開始される場合の両方がある）
- 依存されるFR：FR-03（登録済みの本が前提）、FR-07（登録済みの本が削除対象になる）

#### 入力
| フィールド | 型 | 必須 | 説明 |
|---|---|---|---|
| `title` | string | ✅ | 本のタイトル。空文字は不可 |
| `author` | string | ❌ | 著者名。未入力時は「著者不明」として保存する |
| `coverImage` | image | ❌ | `PhotosPicker` でカメラロールから選択。未選択時は表紙なし（プレースホルダー画像を表示） |

#### 処理フロー
1. 本棚一覧画面（SCR-01）右上の「＋」→「手入力で登録する」、またはFR-01からの遷移でSCR-03を開く
2. タイトル（必須）・著者（任意）・表紙画像（任意）を入力する
3. 「登録する」ボタンをタップする
   - `title` が空文字 → 「タイトルを入力してください」とフィールド下部に赤字表示し、登録処理を中断する
   - `title` が入力済み → SwiftDataに `Book`（`author` 未入力時は `"著者不明"` を保存）として保存し、本棚一覧画面（SCR-01）へ遷移する

#### 異常系
- 選択した画像データの読み込みに失敗 → 「画像を読み込めませんでした。表紙なしで登録しますか？」と確認ダイアログを表示し、「はい」で `coverImage` なしのまま保存する。「いいえ」の場合は画像選択からやり直せる状態でSCR-03に留まる

#### 画面表示例（正常系）
本棚一覧画面（SCR-01）に新規登録した本のカードが追加表示される。

#### 画面表示例（異常系）
```
「タイトルを入力してください」（赤字、titleフィールド下部）
```

### FR-03：メモ記録

#### 概要（1行）
1冊の本につき1日1件、読書内容や気づきを箇条書き形式（複数の入力フォーム）でメモとして記録する。

#### 対応する画面 / インターフェース
- `SCR-05 本詳細画面（メモ一覧）` → `SCR-06 メモ入力画面`

#### 依存関係
- 依存するFR：FR-01 または FR-02（本が登録済みであること）
- 依存されるFR：FR-04（メモ内容がAI対話の起点になる）、FR-05（メモが要約の材料になる）、FR-07（登録済みのメモが削除対象になる）、FR-09（メモ内容がアドバイス生成の材料になる）

#### 入力
| フィールド | 型 | 必須 | 説明 |
|---|---|---|---|
| `contentItems` | [String] | ✅（配列全体として） | 箇条書きの各項目に対応する文字列の配列。SCR-06の入力フォーム1つにつき配列の1要素が対応する。保存時に空文字（前後の空白のみを含む場合も空文字とみなす）の要素は自動的に除外される。除外後の配列が1件以上であることが保存可能の条件（配列内の各要素は個別には必須ではない） |

#### 処理フロー
1. 本詳細画面（SCR-05）で「今日のメモを書く」ボタン、またはメモカードの編集アイコン（✎）をタップする
2. 端末のローカルタイムゾーン（`Calendar.current`）で当日日付を判定する
   - 当日分の `MemoEntry`（対象の `bookId` かつ日付が当日）が存在しない → SCR-06を、1行分の空欄入力フォーム1つのみを表示した新規状態で開く
   - 当日分の `MemoEntry` が既に存在する → 確認ダイアログを挟まず、既存の `MemoEntry.contentItems` の各要素をそれぞれ1つの入力フォームに読み込んだ状態（フォーム数＝要素数）で、即座に上書き編集できる状態でSCR-06を開く（1日1件の制約を「後勝ち」で運用する方針は変更しない）
3. SCR-06で箇条書き項目を入力する
   - 各フォームは1行分のテキスト入力欄（`TextField`相当）
   - フォームの下（または横）に配置された「＋」ボタンをタップするたびに、新しい空欄の入力フォームが一番下に追加される（複数の箇条書き項目を作成できる）
   - 各フォームには削除ボタンが配置されており、タップするとそのフォーム（および入力済みの内容）を削除する
4. 画面下部に固定表示されたフローティングボタン（保存ボタン。SCR-05の「今日のメモを書く」ボタンと同様の配置パターン）をタップする
   - 保存処理の直前に、各フォームの値から空文字（前後の空白のみの場合を含む）の項目を除外する
   - 除外した結果、1件も項目が残らない（＝すべてのフォームが未入力） → 「メモを入力してください」と表示し、保存処理を中断する
   - 除外した結果、1件以上の項目が残る → 残った項目をフォームの表示順（上から順）のまま配列として、SwiftDataに `MemoEntry`（`bookId`・`date`・`contentItems`）として保存する（Step2で既存メモがあった場合は同一レコードを更新する）
5. 保存成功後、「AIと対話して深掘りする」の確認を表示する（FR-04へ）
6. メモの記録・保存・閲覧はSwiftDataへのローカル書き込みのみで完結するため、ネットワーク接続がない状態（オフライン）でも実行できる

#### 異常系
- 保存ボタンタップ後、保存処理完了前にアプリプロセスが強制終了された場合 → そのメモは保存されない（ローカルDBへの書き込みのため通信起因の失敗はない。次回起動時、当日分のメモは未作成の状態としてStep2の判定が行われる）

#### 画面表示例（正常系）
```
SCR-06入力例：
・「主体的である」の章を読み返した
・反応的な自分に気づけた
[＋]（新しい入力フォームを追加）
```
保存後、本詳細画面（SCR-05）のメモ一覧の先頭（日付降順）に、本日の日付のメモカードが追加表示される。カード本文プレビューは箇条書き（各項目の先頭に「・」）で表示される。

#### 画面表示例（異常系）
```
「メモを入力してください」（赤字、入力フォーム群の下部）
```

### FR-04：AI対話フィードバック

#### 概要（1行）
記録したメモに対し、Gemini APIが言語化・具体性向上を目的とした質問を複数往復の会話形式で投げかけ、対話ログを保存する。

#### 対応する画面 / インターフェース
- `SCR-07 AI対話画面（チャット形式）`

#### 依存関係
- 依存するFR：FR-03（その日のメモが保存済みであること）
- 依存されるFR：FR-05（対話ログが要約の材料になる）、FR-07（保存済みの対話ログが削除対象になる）、FR-08（保存済みの対話ログが振り返り閲覧の対象になる）、FR-09（対話ログがアドバイス生成の材料になる）

#### 入力
| フィールド | 型 | 必須 | 説明 |
|---|---|---|---|
| `memoContent` | string | ✅ | FR-03で保存したその日のメモ本文（`MemoEntry.contentItems`の各要素を改行で連結した1つの文字列。FR-03参照。初回のAIリクエストのコンテキストとして使用） |
| `userReply` | string | ✅（2ターン目以降） | ユーザーがAIの質問に対して入力する回答 |

#### 処理フロー
1. FR-03でのメモ保存後、「AIと対話して深掘りする」の確認でユーザーが「はい」を選択し、SCR-07を開く
2. アプリはCloudflare Workers経由でGemini API（`gemini-3.1-flash-lite`）にメモ本文を送信し、最初の質問を生成する
   - `POST {CLOUDFLARE_WORKERS_URL}/chat`、ボディに `bookTitle`・`memoContent`・`conversationHistory`（初回は空配列）を含める
   - リクエストヘッダーに `X-Shared-Secret`（NF-02参照）を付与する
   - タイムアウト：15秒（FR-06共通ルール参照）
3. AIからの質問をチャット画面（SCR-07）に表示し、ユーザーがテキスト入力欄に回答を入力して送信する。SCR-07右上には常時「終了する」ボタンを表示する
4. 送信のたびに `conversationHistory` に往復を追加してStep2と同じエンドポイントへ再送し、AIの次の質問を取得する
5. 会話の終了条件は以下の2つを併用する（いずれか一方が成立した時点で会話を終了する）
   - 往復上限：ユーザーの回答が5往復（AIの質問5回・ユーザーの回答5回）に達したら、それ以上AIへのリクエストは行わずアプリ側で会話を終了する。終了時、SCR-07に「言語化についてのAI対話は今回はここまでです。お疲れさまでした」という終了メッセージを表示する
   - 終了ボタン：ユーザーがSCR-07右上の「終了する」ボタンをタップした時点（往復回数によらずいつでも押せる）で会話を終了する
6. 会話終了時、その日の対話ログ（メモ本文＋それまでに成立した質問と回答の全往復）をSwiftDataに `ConversationLog`（`bookId`・`date`・`turns`：質問と回答のペア配列）として保存する

#### 異常系
- Gemini API呼び出し失敗（Cloudflare Workers経由のエラー・タイムアウト15秒） → 「AIとの通信に失敗しました。もう一度お試しください」と表示し、「再試行」ボタンを表示する（FR-06共通ルールの通り自動リトライは行わない）
- ネットワーク接続なし → 「インターネットに接続されていません」と表示し、「本詳細画面に戻る」ボタンのみ表示する（オフラインでのAI対話は不可）
- 無料枠超過（Cloudflare Workers経由でGemini APIが429を返す） → 「本日のAI対話の利用上限に達しました。しばらく時間をおいてから再度お試しください」と表示する
- 対話の途中（1ターン目のAI質問受信後〜会話終了前）でユーザーがアプリを閉じた、またはホーム画面に戻った場合 → それまでの往復は保存せず破棄する。次回SCR-05を開いたときは当日分の `ConversationLog` が存在しない状態（＝FR-04を最初からやり直す状態）になる

#### 会話例（正常系）
```
AI: 「『自分の意見を言えるようになりたい』とありますが、直近で意見を言えなかった具体的な場面はありますか？」
ユーザー: 「今日の会議で発言を求められたが黙ってしまった」
AI: 「そのとき、何を言おうとして、なぜ言えなかったのですか？」
ユーザー: 「反論されるのが怖くて、無難な相槌で済ませた」
AI: 「次に同じ場面が来たとき、どんな一言なら言えそうですか？」
（以降、終了条件を満たすまで継続）
```

#### 会話例（異常系）
```
「AIとの通信に失敗しました。もう一度お試しください」
[再試行]
```

### FR-05：本単位の要約生成

#### 概要（1行）
1冊の本に蓄積された全メモ・全AI対話ログを、ユーザーが要約タブ内の「要約を作成する」ボタンを押した時点でのみGemini APIにより要約し、SwiftDataにキャッシュして表示する。

#### 対応する画面 / インターフェース
- `SCR-08 要約画面`（SCR-05内の「要約」タブとして配置）

#### 依存関係
- 依存するFR：FR-03（メモ）、FR-04（対話ログ）
- 依存されるFR：なし

#### 入力
| フィールド | 型 | 必須 | 説明 |
|---|---|---|---|
| `bookId` | UUID | ✅ | 要約対象の本のID |
| `memos` | MemoEntry[] | ✅ | その本に紐づく全メモ（日付降順）。Gemini APIへ送信する際、各メモの本文は`MemoEntry.contentItems`の各要素を改行で連結した1つの文字列として扱う（FR-03参照） |
| `conversationLogs` | ConversationLog[] | ❌ | その本に紐づく全AI対話ログ。存在しない場合は空配列 |

#### 処理フロー
1. 本詳細画面（SCR-05）で「要約」タブ（SCR-08）をタップする
2. `Book.cachedSummary` が既に存在する場合 → Gemini APIは呼び出さず、保存済みの要約テキストと生成日時（`Book.cachedSummaryGeneratedAt`）をSCR-08にそのまま表示する。存在しない場合 → 「まだ要約が作成されていません」という空状態メッセージを表示する
3. その本に紐づく `MemoEntry` が0件の場合 → SCR-08の「要約を作成する」ボタンを非活性（disabled）にし、「メモを記録すると要約を作成できます」と表示する
4. `MemoEntry` が1件以上ある場合 → SCR-08に「要約を作成する」ボタンを活性状態で表示する。`Book.cachedSummary` が既に存在する場合はボタンのラベルを「要約を再作成する」に変える
5. ユーザーが「要約を作成する」（または「要約を再作成する」）ボタンをタップする（このタップだけがGemini API呼び出しのトリガーであり、Step1〜4の画面表示だけではAPIは呼び出されない）
6. アプリはボタンをローディング状態（スピナー表示・非活性）にし、Cloudflare Workers経由でGemini API（`gemini-3.1-flash-lite`）に、その時点の最新の全メモ本文・全対話ログを送信する
   - `POST {CLOUDFLARE_WORKERS_URL}/summarize`、ボディに `bookTitle`・`memos`（日付＋本文の配列）・`conversationLogs` を含める
   - リクエストヘッダーに `X-Shared-Secret`（NF-02参照）を付与する
   - タイムアウト：15秒（FR-06共通ルール参照）
7. 生成された要約テキストを `Book.cachedSummary` に、生成時刻を `Book.cachedSummaryGeneratedAt` に保存する（既存のキャッシュがあれば上書きする）。保存後、SCR-08に新しい要約テキストを表示し、ボタンを通常状態に戻す
8. 以降、ユーザーが再度ボタンをタップしない限り再生成は行われない。SCR-08を再度開いた際はStep2の通り、保存済みの `Book.cachedSummary` がそのまま表示される（本に「読了」等のステータスは持たせず、ユーザーが任意のタイミングでボタンを押す運用とする）

#### 異常系
- Gemini API呼び出し失敗・タイムアウト（15秒） → 「要約の生成に失敗しました」と表示し、「再試行」ボタンを表示する。`Book.cachedSummary` は変更せず、失敗前に表示していたキャッシュ済み要約（存在する場合）の表示をそのまま維持する
- ネットワーク接続なし（ボタンタップ時） → Gemini APIを呼び出さず「インターネットに接続されていないため要約を作成できません」と表示する。`Book.cachedSummary` が既に存在する場合、Step2によるキャッシュ済み要約の閲覧自体はオフラインでも可能
- 無料枠超過（429） → 「本日の要約生成の利用上限に達しました」と表示する。`Book.cachedSummary` は変更しない

#### 画面表示例（正常系）
```
【この本から得た気づき】
・「小さな一歩を積み重ねる」という考え方について、3回のメモで繰り返し言及している
・4/12の対話で「完璧主義をやめる」という具体的な行動目標が明確化された

最終生成：2026/08/05
[要約を再作成する]
```

#### 画面表示例（異常系）
```
「まだ要約が作成されていません」（要約タブ内、空状態）
[要約を作成する]（メモ0件の場合は非活性）
```

### FR-06：共通ルール（外部API連携・エラーハンドリング）

#### 概要（1行）
全FRに横断的に適用される、Gemini API・国立国会図書館サーチAPI連携時の共通ルールを定義する。

#### 適用対象
- FR-01（NDL API連携）、FR-04・FR-05・FR-09（Gemini API連携）

#### 共通ルール一覧
| # | ルール | 内容 |
|---|---|---|
| 1 | Cloudflare Workers経由の通信 | iOSアプリはGemini APIキーを保持しない。AI関連の全リクエストは環境変数 `CLOUDFLARE_WORKERS_URL`（architecture.mdで定義）を経由する |
| 2 | タイムアウト値の統一 | 国立国会図書館サーチAPI：10秒。Gemini API（Cloudflare Workers経由）：15秒。超過時は各FRの異常系メッセージを表示する |
| 3 | 自動リトライなし | 外部API呼び出し失敗時、アプリ側での自動リトライは行わない。ユーザー操作（「再試行」ボタンのタップ）を起点にのみ再送する |
| 4 | エラーメッセージのトーン統一 | ユーザー向けエラーメッセージは「〜に失敗しました」「〜できませんでした」で統一し、HTTPステータスコード・スタックトレース等の技術的情報は画面に表示しない |
| 5 | ログ出力 | 外部API呼び出しのエラー（ステータスコード・エンドポイント・タイムスタンプ）をXcodeコンソールログに出力する。メモ本文・対話内容・個人情報はログに出力しない |
| 6 | 共有シークレット検証 | FR-04・FR-05・FR-09のリクエストには `X-Shared-Secret` ヘッダー（NF-02参照）を付与する。Cloudflare Workers側の環境変数 `WORKERS_SHARED_SECRET` と一致しない場合、WorkersはGemini APIを呼び出さずHTTP 401を返す。アプリ側はこの401を通常の「Gemini API呼び出し失敗」と同一のエラーメッセージ（FR-04・FR-05・FR-09の異常系）として扱い、技術的な理由（401である旨）はXcodeコンソールログにのみ出力する |

### FR-07：本・メモ・対話ログの削除

#### 概要（1行）
本棚一覧画面・本詳細画面から、本単位またはメモ単位で登録済みデータを削除する。本単位の削除は紐づくメモ・対話ログ・キャッシュ要約もすべて削除するカスケード削除とする。

#### 対応する画面 / インターフェース
- 本単位の削除：`SCR-01 本棚一覧画面`（本カードのスワイプ操作から「削除」ボタンを表示）
- メモ単位の削除：`SCR-05 本詳細画面（メモ一覧）`（メモカードのスワイプ操作から「削除」ボタンを表示）

#### 依存関係
- 依存するFR：FR-01 または FR-02（削除対象の本が登録済みであること）、FR-03（メモ単位削除の場合、削除対象のメモが登録済みであること）
- 依存されるFR：なし

#### 入力
| フィールド | 型 | 必須 | 説明 |
|---|---|---|---|
| `bookId` | UUID | ✅（本単位の削除時） | 削除対象の本のID |
| `memoEntryId` | UUID | ✅（メモ単位の削除時） | 削除対象のメモのID |

#### 処理フロー（本単位の削除）
1. SCR-01で対象の本カードを左スワイプし、「削除」ボタンをタップする
2. 確認ダイアログ「『{タイトル}』を削除しますか？この本に紐づくメモ・AI対話ログ・要約もすべて削除され、元に戻せません」を表示する
3. 「削除する」をタップする → 対象の `Book` を削除する。SwiftDataのリレーションシップ（`Book` → `MemoEntry`・`Book` → `ConversationLog`）にカスケード削除ルール（`.cascade`）を設定し、`Book` の削除と同一トランザクションで、紐づく全 `MemoEntry`・全 `ConversationLog`・`Book.cachedSummary`（および `cachedSummaryGeneratedAt`）を削除する
   - 「キャンセル」をタップする → 何も削除せずSCR-01に留まる
4. 削除完了後、SCR-01の本棚一覧から該当カードを即座に取り除く

#### 処理フロー（メモ単位の削除）
5. SCR-05のメモ一覧で対象のメモカードを左スワイプし、「削除」ボタンをタップする
6. 確認ダイアログ「このメモを削除しますか？同じ日のAI対話ログも削除され、元に戻せません」を表示する
7. 「削除する」をタップする → 対象の `MemoEntry` を削除する。同一 `bookId`・同一 `date` に紐づく `ConversationLog`（FR-04で保存済みの場合）もあわせて削除する。`Book.cachedSummary` は削除しない（次回FR-05の「要約を再作成する」実行時に、削除後の残存データをもとに上書きされる）
   - 「キャンセル」をタップする → 何も削除せずSCR-05に留まる
8. 削除完了後、SCR-05のメモ一覧から該当カードを即座に取り除く

#### 異常系
- 削除処理はSwiftDataへのローカル書き込みのみで完結するため、通信起因の失敗は発生しない
- 「削除する」タップ後、SwiftDataの `save()` 完了前にアプリプロセスが強制終了された場合 → `Book` とカスケード対象（`MemoEntry`・`ConversationLog`・`cachedSummary`）、または `MemoEntry` と連動削除対象（同日の `ConversationLog`）は同一トランザクションとして扱われるため、一部だけ削除された不整合状態は発生しない（次回起動時、削除前・削除後いずれかの状態で確定している）

#### 画面表示例（正常系）
```
「『嫌われる勇気』を削除しますか？
この本に紐づくメモ・AI対話ログ・要約もすべて削除され、元に戻せません」
[キャンセル]　[削除する]
```

#### 画面表示例（異常系）
該当なし（削除処理はローカル完結のため、通信エラー等による異常系画面は発生しない）

### FR-08：AI対話ログの振り返り閲覧

#### 概要（1行）
メモカードから、その日に記録したAI対話ログ（`ConversationLog`）を読み取り専用で振り返る。

#### 対応する画面 / インターフェース
- `SCR-05 本詳細画面（メモ一覧）`（メモカードの振り返りアイコン）
- `SCR-07 AI対話画面`（読み取り専用モードとして再利用。新しい画面IDは作らない）

#### 依存関係
- 依存するFR：FR-04（その日の対話ログが保存済みであること）
- 依存されるFR：なし

#### 入力
| フィールド | 型 | 必須 | 説明 |
|---|---|---|---|
| `bookId` | UUID | ✅ | 振り返り対象の本のID |
| `date` | Date | ✅ | 振り返り対象のメモの日付（同一 `bookId`・同一 `date` の `ConversationLog` を特定するキー） |

#### 処理フロー
1. SCR-05のメモ一覧を表示する時点で、アプリは各メモカードについて同一 `bookId`・同一 `date` の `ConversationLog` が存在するかを判定する
   - 存在する → メモカードの3つ目のアイコン（振り返りアイコン。編集・削除アイコンに並べて配置）を活性状態で表示する
   - 存在しない → 振り返りアイコンを非活性（グレーアウト）状態で表示し、タップを受け付けない
2. ユーザーが活性状態の振り返りアイコンをタップする
3. アプリは該当する `ConversationLog` を読み込み、SCR-07を**読み取り専用モード**で開く
   - 読み取り専用モードでは、通常モード（FR-04）で表示するテキスト入力欄・送信ボタン・往復進捗表示（「往復n/5」）・「終了する」ボタンは表示しない
   - 代わりに、保存済みの `turns`（質問と回答のペア配列）をチャット形式でそのまま上から順に表示し、画面上部に「閉じる」ボタンのみを表示する
   - 読み取り専用モードではGemini APIへのリクエストは一切発生しない（Cloudflare Workers経由の通信を含め、外部通信を行わない）
4. ユーザーが「閉じる」ボタンをタップする → SCR-05（本詳細画面・メモ一覧）に戻る

#### 異常系
- 該当なし。振り返り対象は常にローカルのSwiftDataに保存済みの `ConversationLog` であり、外部API通信を行わないため、通信エラー・タイムアウト等は発生しない。対話ログが破損している場合の考慮も行わない（Phase 1のスコープ外）

#### 画面表示例（正常系）
```
[SCR-05 メモカード]
2026/07/28のメモ　[編集] [削除] [吹き出しアイコン：振り返り（活性）]

[SCR-07 読み取り専用モード]
AI: 「『自分の意見を言えるようになりたい』とありますが、直近で意見を言えなかった具体的な場面はありますか？」
ユーザー: 「今日の会議で発言を求められたが黙ってしまった」
AI: 「そのとき、何を言おうとして、なぜ言えなかったのですか？」
ユーザー: 「反論されるのが怖くて、無難な相槌で済ませた」
（以降、保存済みの全turnsを表示）

[閉じる]
```

#### 画面表示例（異常系）
該当なし（対話ログが存在しない日のメモカードは振り返りアイコン自体が非活性になり、SCR-07を開く操作自体が発生しない）

### FR-09：今日のアドバイスの自動生成

#### 概要（1行）
メモ記録フローが完了した時点で、その日のメモ内容（＋対話ログがあれば対話内容も）をもとにAIが「今日のアドバイス」を自動生成し、メモカードの付箋（常時表示、開閉操作なし）で閲覧できるようにする。

#### 対応する画面 / インターフェース
- `SCR-06 メモ入力画面`（対話スキップ時のトリガー元）
- `SCR-07 AI対話画面`（対話終了時のトリガー元）
- `SCR-05 本詳細画面（メモ一覧）`（メモカードの付箋での常時表示）

#### 依存関係
- 依存するFR：FR-03（メモ保存。アドバイス生成の起点かつ必須の入力材料）、FR-04（対話ログが存在する場合、任意の入力材料として使用）
- 依存されるFR：なし

#### 入力
| フィールド | 型 | 必須 | 説明 |
|---|---|---|---|
| `memoContent` | string | ✅ | その日の `MemoEntry.contentItems` の各要素を改行で連結した1つの文字列（FR-03参照。アドバイス生成の起点となるメモ本文） |
| `conversationTurns` | ConversationTurn[] | ❌ | その日の `ConversationLog.turns`。AI対話（FR-04）を実施した場合のみ使用し、対話をスキップした場合は空配列として扱う |

#### 処理フロー
1. トリガー経路A（対話スキップ時）：SCR-06でメモ保存後の確認ダイアログ「AIと少し話してみますか？」（DLG-04）で「いいえ」を選択した時点で、**メモ内容のみ**を入力としてアドバイス生成をトリガーする
2. トリガー経路B（対話実施時）：「はい」を選択しFR-04のAI対話を行った場合、対話終了時点（往復上限5回到達、またはSCR-07右上「終了する」ボタンのタップ）で、**メモ内容＋その日の対話ログ全体**を入力としてアドバイス生成をトリガーする
   - FR-04の補足（対話が1ターンも成立していない状態での終了）により `ConversationLog` が保存されなかった場合は、トリガー経路Aと同様に**メモ内容のみ**を入力として扱う
3. いずれの経路も、ユーザーの明示的な追加操作（ボタン押下）は不要とする（FR-05の要約生成とは異なり、完全自動生成とする）
4. トリガー発生後、アプリはバックグラウンドでCloudflare Workers経由でGemini API（`gemini-3.1-flash-lite`）を呼び出す
   - `POST {CLOUDFLARE_WORKERS_URL}/advice`、ボディに `bookTitle`・`memoContent`・`conversationTurns`（対話ログがない場合は空配列）を含める
   - リクエストヘッダーに `X-Shared-Secret`（NF-02参照）を付与する
   - タイムアウト：15秒（FR-06共通ルール参照）
   - この呼び出しはユーザーの画面遷移操作をブロックしない（SCR-05・SCR-06・SCR-07間の遷移は生成完了を待たずに行われる）
5. 生成成功時、レスポンステキストを対象の `MemoEntry.dailyAdvice` に保存する
6. SCR-05のメモカードに「今日のアドバイス」付箋を配置し、開閉操作なしで未生成・生成中・生成成功・生成失敗のいずれの状態も常時表示する（2026-08-13モックレビューフィードバックにより、当初のアコーディオン展開トグル方式から常時表示方式に変更。basic_design.md Section 4 SCR-05参照）
   - 生成中（トリガー発生後、レスポンス未受信）の間は付箋内にローディング表示（スピナー）を常時表示する
   - 生成成功済み（`dailyAdvice` が値を持つ）の場合 → 保存済みのテキストを付箋内にそのまま常時表示する
   - 生成失敗（`dailyAdvice` が `nil` のまま。異常系参照）の場合 → 付箋内にエラーメッセージと「再試行」ボタンを常時表示する

#### 異常系
- Gemini API呼び出し失敗・タイムアウト（15秒） → `dailyAdvice` は `nil` のまま保持する。メモカードの付箋に「アドバイスの生成に失敗しました」を常時表示し、「再試行」ボタンを表示する（FR-05 ERR-12のパターンを踏襲）。「再試行」タップ時はStep4と同一のリクエストを再送する
- ネットワーク接続なし（トリガー時点） → Gemini APIを呼び出さず、`dailyAdvice` は `nil` のまま保持する。メモカードの付箋に「インターネットに接続されていないためアドバイスを生成できませんでした」を常時表示し、「再試行」ボタンを表示する（オンライン復帰後にユーザー操作で再試行できるようにするため。FR-05のオフライン系異常系とは異なり、トリガーが自動発生のためボタンなしでは再試行手段がなくなる点を考慮した）
- 無料枠超過（Cloudflare Workers経由でGemini APIが429を返す） → `dailyAdvice` は `nil` のまま保持する。メモカードの付箋に「本日のアドバイス生成の利用上限に達しました」を常時表示する（FR-05 ERR-14と同様、時間経過でしか解消しないため「再試行」ボタンは表示しない）
- 対話終了時点（トリガー経路B）でトリガーが発生した後、生成完了前にユーザーがアプリを終了した場合 → 生成中リクエストは破棄され、`dailyAdvice` は `nil` のまま保持される（次回SCR-05を開いた際、付箋は「生成に失敗しました」ではなく未生成状態として扱う。要確認事項参照）

#### 画面表示例（正常系）
```
[SCR-05 メモカード]
2026/07/30のメモ　💬(非活性) ✎ 🗑
・「主体的である」の章を読み返した
・反応的な自分に気づけた一日だった
┌ 今日のアドバイス（付箋・常時表示） ─────┐
「今日の気づきを次に活かすには、まず小さな一歩から始めてみましょう。
『反応的な自分に気づけた』と気づけたこと自体が、すでに大きな前進です」
└─────────────────────────────┘
```

#### 画面表示例（異常系）
```
┌ 今日のアドバイス（付箋・常時表示） ─────┐
「アドバイスの生成に失敗しました」
[再試行]
└─────────────────────────────┘
```

## 非機能要件

### NF-01：レスポンスタイム
- 国立国会図書館サーチAPI・Gemini API（Cloudflare Workers経由）の呼び出しは、いずれも同期的なリクエスト/レスポンスとして扱う。タイムアウト値はFR-06共通ルールNo.2の通り（NDL：10秒、Gemini：15秒）
- バーコードスキャン処理（VisionKit `DataScannerViewController`）はリアルタイム処理であり、UIスレッドをブロックしない
- → architecture.mdの非同期処理設計・setup.mdの動作確認チェックに引き継ぐ

### NF-02：セキュリティ・認証
- 本アプリは個人利用（1ユーザー）のみのため、アプリ内でのユーザー認証・ログイン機能は実装しない
- Gemini APIキーはiOSアプリ内に保持せず、Cloudflare Workers側の環境変数として管理する（変数名：`GEMINI_API_KEY`）→ architecture.mdの環境変数セクションに転記する
- 国立国会図書館サーチAPIは認証不要（個人・非営利利用は申請不要）
- iOSアプリ→Cloudflare Workers間のリクエスト正当性検証：共有シークレット方式を採用する。Cloudflare Workersのエンドポイントは仕組み上インターネットに公開されるため、URLが第三者に知られた場合の悪用（Gemini API無料枠の消費等）を防ぐ最低限の対策とする
  - iOSアプリは `/chat`（FR-04）・`/summarize`（FR-05）・`/advice`（FR-09）への全リクエストのHTTPヘッダーに `X-Shared-Secret: {シークレット値}` を付与する
  - Cloudflare Workers側は環境変数 `WORKERS_SHARED_SECRET` に設定した値とヘッダー値を比較し、一致しない場合はGemini APIを呼び出さずHTTP 401を返す（FR-06共通ルールNo.6参照）
  - iOSアプリ側でのシークレット値の埋め込み方法（Xcode Build Settings経由等）はarchitecture.md・setup.mdで具体化する
  - → architecture.mdの環境変数セクション（`WORKERS_SHARED_SECRET`）・システム構成図（検証ステップ）に転記する。setup.mdのCloudflare Workers設定手順にも反映する

### NF-03：入力バリデーション
- タイトル（FR-02）・メモ本文（FR-03）：空文字不可。クライアント側（SwiftUI）でバリデーションし、該当フィールド下部に赤字でエラーメッセージを表示する
- Gemini APIのレスポンス（AIの質問文・要約文）はプレーンテキストとして扱い、JSON形式のレスポンスは期待しない。Cloudflare Workers側でGemini APIレスポンスの形式異常（空文字、極端に長い等）を検知した場合はHTTP 500を返し、iOSアプリ側はFR-06共通ルールNo.4のフォーマットでエラーメッセージを表示する
- → basic_design.mdのエラー定義に転記する

### NF-04：エラーハンドリング・ログ
- 外部APIエラー（国立国会図書館サーチAPI・Gemini API）ごとの挙動は各FRの異常系に記載の通り
- リトライ：しない（FR-06共通ルールNo.3）
- ログ出力：外部API呼び出しのステータスコード・エンドポイント・タイムスタンプをXcodeコンソールに出力する。メモ本文・対話内容は出力しない
- → basic_design.mdのエラー定義一覧に転記する

### NF-05：データ保持・レート制限
- データ保持期間：制限なし。SwiftDataにローカル永続保存し、ユーザーが手動で削除しない限り保持する
- 削除機能：本・メモ・対話ログの削除をPhase 1のスコープに含める。削除の粒度（本単位のカスケード削除・メモ単位の削除）と確認ダイアログの仕様はFR-07に定義する
- Gemini APIのレート制限（無料枠）への対応：FR-04・FR-05の異常系「無料枠超過時」に記載の通り、429応答時はユーザー向けメッセージを表示する。無料枠の正確なRPM/RPD上限値は現時点で未確認（progress.mdの「未回答の要確認事項」を参照。Phase 1実装時に再確認する）
- → business.mdの運用フローに引き継ぐ

### NF-06：オフライン対応
- オフラインでも動作する機能：FR-02（手入力での本登録）、FR-03（メモの記録・保存・閲覧）、FR-07（本・メモ・対話ログの削除）、過去に保存済みの `ConversationLog` の閲覧、およびFR-05のキャッシュ済み要約（`Book.cachedSummary`）の閲覧。いずれもSwiftDataへのローカル読み書きのみで完結する
- ネットワーク接続が必須の機能：FR-01のバーコードスキャンによる書誌情報取得（国立国会図書館サーチAPI）、FR-04のAI対話（Gemini API）、FR-05の要約の新規作成・再作成（「要約を作成する」ボタンタップ時のGemini API呼び出し）
- ネットワーク接続がない状態でオフライン必須機能が呼び出された場合の挙動は、各FRの異常系（FR-01・FR-04・FR-05）に記載の通り
